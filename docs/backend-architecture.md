# طرح بک‌اند DeliShop (نسخه‌ی قدیمی — دیگر پیاده‌سازی نمی‌شود)

> **این سند منسوخ شده است.** طرح اولیه (Node.js/Hono/PostgreSQL روی لیارا) کنار گذاشته شد و
> به‌جایش یک بک‌اند PHP/MySQL ساده روی همون هاست اشتراکی cPanel نوشته شد (بدون هزینه‌ی
> اضافه). برای معماری واقعی که الان دیپلوی می‌شود، `server-php/README.md` و `DEPLOY.md`
> را ببینید. این سند فقط برای مرجع تاریخی نگه داشته شده — API contract (مسیرها، شکل
> پاسخ‌ها، رفتار session) همینی است که اینجا توصیف شده و بدون تغییر در بازنویسی PHP هم
> رعایت شده، پس بخش‌های §۲ تا §۵ (مدل داده، مسیر API، auth) هنوز به‌عنوان مرجع رفتار درستند؛
> فقط §۶ و §۷ (زیرساخت/دیپلوی/لیارا) دیگر صدق نمی‌کنند.

این طرح از روی کد فعلی فرانت‌اند (`app/`) نوشته شده است: صفحه‌های فروشگاه، سبد، پرداخت، استودیو و ورود. هر چیزی که الان در `localStorage` مرورگر نگه داشته می‌شود (محصولات، محصولات پنهان‌شده، سفارش‌ها) و ورود استودیو که فعلاً فقط در مرورگر چک می‌شود، به سرور منتقل می‌شود.

**فرض‌ها** (اگر درست نیستند، بخش‌های مربوط باید عوض شوند):

- سایت برای مشتری‌های داخل ایران است و روی هاست ایرانی اجرا می‌شود (قیمت به تومان، پرداخت کارت‌به‌کارت با آپلود رسید، شماره‌ی موبایل ۰۹…).
- یک نفر (یا دو سه نفر) فروشگاه را مدیریت می‌کند. مشتری‌ها حساب کاربری ندارند.
- ترافیک کم است: حداکثر چند ده سفارش در روز. یک سرور کافی است.
- یک توسعه‌دهنده آن را می‌سازد، پس سادگی از مقیاس‌پذیری مهم‌تر است.

## ۱. انتخاب تکنولوژی‌ها

| بخش | انتخاب | چرا |
| --- | --- | --- |
| زبان و ران‌تایم | Node.js 22 + TypeScript | همان زبانِ فرانت‌اند است؛ نوع‌ها (types) بین دو طرف مشترک می‌شوند. |
| فریم‌ورک API | [Hono](https://hono.dev) روی `@hono/node-server` | سبک و TypeScript-محور است؛ میان‌افزارهای کوکی، CSRF، هدرهای امنیتی و محدودیت حجم بدنه را خودش دارد؛ کلاینت RPC تایپ‌شده برای فرانت‌اند می‌دهد. Express هم کار می‌کند ولی تایپ ضعیف‌تری دارد. |
| سبک API | REST با JSON، و `multipart/form-data` برای آپلود فایل | منابع کم و ساده‌اند (محصول، سفارش، ورود). GraphQL یا tRPC اینجا فقط پیچیدگی اضافه می‌کنند. |
| اعتبارسنجی ورودی | Zod (با `@hono/zod-validator`) | یک اسکیمای واحد هم ورودی را چک می‌کند هم نوع TypeScript می‌سازد. |
| پایگاه داده | PostgreSQL 16 | هاست‌ها نسخه‌ی مدیریت‌شده با بکاپ روزانه دارند. SQLite هم برای این حجم کافی بود، ولی روی PaaS به دیسک دائمی و بکاپ دستی نیاز دارد. |
| ORM و مایگریشن | Drizzle ORM + drizzle-kit | اسکیمای TypeScript، کوئری‌های نزدیک به SQL، مایگریشن‌های SQL خوانا. |
| ذخیره‌ی فایل | Object Storage سازگار با S3 (لیارا یا ابر آروان) با `@aws-sdk/client-s3`؛ در توسعه‌ی محلی، پوشه‌ی `uploads/` روی دیسک | عکس نقاشی، عکس محصول، صدای داستان و رسید پرداخت نباید داخل دیتابیس بروند. |
| پردازش تصویر | sharp | کوچک کردن، تبدیل به WebP و حذف متادیتای EXIF (از جمله موقعیت GPS عکس‌های موبایل). |
| هش رمز عبور | argon2id با `@node-rs/argon2` | الگوریتم پیشنهادی فعلی برای رمز عبور؛ نسخه‌ی آماده (prebuilt) دارد و کامپایل نمی‌خواهد. |
| ورود | نشست (session) سمت سرور + کوکی `HttpOnly` | ساده‌ترین روش امن برای یک پنل مدیریت هم‌دامنه. توضیح در بخش ۵. |
| محدودیت نرخ درخواست | `hono-rate-limiter` با حافظه‌ی داخلی | برای یک سرور کافی است؛ با چند سرور باید Redis اضافه شود. |
| لاگ | pino | لاگ JSON که در داشبورد هاست قابل جست‌وجوست. |
| تست | Vitest + `app.request()` خود Hono | تست API بدون بالا آوردن سرور واقعی. |
| داده در فرانت‌اند | TanStack Query | کش، وضعیت بارگذاری و به‌روزرسانی بعد از تغییر؛ جایگزین `useSyncExternalStore` روی localStorage. |
| هاستینگ | لیارا: اپ Node.js + PostgreSQL مدیریت‌شده + Object Storage | هر سه سرویس در یک جا، با TLS خودکار و پرداخت ریالی. جایگزین خارجی: Railway + Cloudflare R2. |
| CI/CD | GitHub Actions | تایپ‌چک، lint، تست و بیلد روی هر push؛ دیپلوی از شاخه‌ی `main`. |

**سرویس‌های بیرونی در MVP:** فقط Object Storage. پیامک به مدیر هنگام سفارش جدید (کاوه‌نگار یا sms.ir) اختیاری است و درگاه پرداخت آنلاین (زرین‌پال و مانند آن) برای بعد می‌ماند (بخش ۷).

## ۲. نمای کلی سیستم

```
 [مرورگر: اپ React]
        │  /api/*   JSON یا multipart، کوکی نشست
        ▼
 [سرور Node + Hono] ───── در production فایل‌های app/dist را هم سرو می‌کند
        │                  │                                  │
        ▼                  ▼                                  ▼
 [PostgreSQL]      [Object Storage]                  [سرویس پیامک، اختیاری]
                    باکت عمومی media:  نقاشی، عکس و صدای محصولات
                    باکت خصوصی receipts: رسیدهای پرداخت
```

فرانت‌اند و API روی **یک دامنه** اجرا می‌شوند (سرور هم `/api/*` را جواب می‌دهد، هم فایل‌های بیلدشده‌ی Vite را با fallback به `index.html` برای مسیرهای React Router). نتیجه: CORS لازم نیست، کوکی ساده کار می‌کند، و یک سرویس دیپلوی می‌شود. در توسعه‌ی محلی، Vite درخواست‌های `/api` را به سرور پروکسی می‌کند.

### مسیر مهم‌ترین کار: ثبت سفارش

1. مشتری در `/checkout` نام، موبایل و عکس رسید را وارد می‌کند و «Send my order» را می‌زند.
2. فرانت‌اند یک `FormData` شامل `name`، `phone`، `items` (شناسه‌ی محصول و تعداد) و فایل `receipt` به `POST /api/orders` می‌فرستد.
3. سرور: محدودیت نرخ ← بررسی Origin (CSRF) ← اعتبارسنجی فیلدها با Zod ← نرمال‌سازی موبایل ← بررسی نوع واقعی و حجم رسید.
4. سرور محصولات را با شناسه از دیتابیس می‌خواند و **قیمت‌ها و جمع کل را خودش حساب می‌کند**؛ قیمتی که مرورگر می‌فرستد هیچ‌وقت قبول نمی‌شود. اگر محصولی حذف شده باشد، `409` برمی‌گردد.
5. رسید با کلید `receipts/{orderId}.{ext}` در باکت خصوصی آپلود می‌شود.
6. در یک تراکنش: شماره‌ی سفارش از sequence گرفته می‌شود و `orders` و `order_items` ذخیره می‌شوند. اگر تراکنش شکست بخورد، فایل رسید پاک می‌شود.
7. پاسخ `201` با شماره‌ی سفارش و جمع کل. فرانت‌اند مهر «PAID / thank you» را نشان می‌دهد و سبد را خالی می‌کند.
8. بعد از پاسخ (ناهمگام): پیامک به مدیر، اگر فعال باشد. شکست پیامک فقط لاگ می‌شود و سفارش را خراب نمی‌کند.

### مسیر افزودن محصول در استودیو

1. مدیر فرم «New product» را پر می‌کند. فرانت‌اند فایل‌ها را به‌صورت `Blob` (نه data URL) در `FormData` به `POST /api/studio/products` می‌فرستد.
2. سرور: بررسی نشست ← اعتبارسنجی ← sharp: نقاشی به WebP روی زمینه‌ی سفید با ضلع حداکثر ۱۲۰۰px، عکس محصول به WebP با حفظ شفافیت و ضلع حداکثر ۱۰۰۰px ← آپلود در باکت عمومی ← ذخیره در دیتابیس.
3. پاسخ `201` با محصول کامل. فرانت‌اند کش لیست محصولات را تازه می‌کند و محصول بلافاصله در فروشگاه دیده می‌شود.

### همگام و ناهمگام

همه‌ی درخواست‌ها همگام‌اند؛ صف لازم نیست. فقط این‌ها در پس‌زمینه‌اند:

- ارسال پیامک سفارش جدید (بعد از commit، بدون انتظار).
- یک کار روزانه داخل همان پروسس (`setInterval` یا cron هاست): حذف نشست‌های منقضی و فایل‌های آپلودشده‌ای که به هیچ ردیفی وصل نیستند.

## ۳. مدل داده

نام جدول‌ها و ستون‌ها `snake_case`، کلیدها `uuid` (با `gen_random_uuid()`)، زمان‌ها `timestamptz`. مقدار enumها عمداً همان رشته‌هایی است که فرانت‌اند الان استفاده می‌کند، تا تبدیل لازم نباشد.

```
Enum: product_category = 'Keychains' | 'Earrings' | 'Pins'
Enum: card_color       = 'mint' | 'pink' | 'orange' | 'purple' | 'yellow' | 'green'
Enum: order_status     = 'awaiting_review' | 'confirmed' | 'shipped' | 'rejected' | 'cancelled'
```

```
Table: admins
- id             (uuid, PK)
- username       (text, unique, not null)      همیشه با حروف کوچک ذخیره می‌شود
- password_hash  (text, not null)              argon2id
- created_at     (timestamptz, not null, default now())
```

```
Table: sessions
- id          (text, PK)        هش SHA-256 توکن داخل کوکی؛ خود توکن هیچ‌جا ذخیره نمی‌شود
- admin_id    (uuid, FK → admins.id, on delete cascade, not null)
- expires_at  (timestamptz, not null)
- created_at  (timestamptz, not null, default now())

Index: sessions(expires_at)   برای کار روزانه‌ی حذف نشست‌های منقضی
```

```
Table: products
- id              (uuid, PK)
- name            (text, not null)
- category        (product_category, not null)
- color           (card_color, not null)         رنگ کارت در فروشگاه
- price           (integer, not null, check price > 0)   به تومان
- story           (text, not null, default '')
- drawing_key     (text, not null)               کلید فایل در باکت عمومی
- drawing_width   (integer, not null)            ابعاد فایل منبع (iw/ih در فرانت‌اند)
- drawing_height  (integer, not null)
- drawing_crop    (jsonb, null)                  فقط برای ۱۶ محصول اولیه: { x, y, w, h, clip }
- photo_key       (text, null)                   عکس واقعی محصول با پس‌زمینه‌ی شفاف
- voice_key       (text, null)                   صدای ضبط‌شده‌ی داستان
- voice_mime      (text, null)
- position        (integer, not null)            ترتیب نمایش در فروشگاه
- archived_at     (timestamptz, null)            حذف نرم
- created_at      (timestamptz, not null, default now())
- updated_at      (timestamptz, not null, default now())

Index: products(position) where archived_at is null
       لیست فروشگاه فقط محصولات فعال را به ترتیب می‌خواند.
Unique index: products(lower(name)) where archived_at is null
       سبد و فروشگاه فعلی محصول را با نام می‌شناسند؛ دو محصول فعال هم‌نام گیج‌کننده است.
```

دکمه‌ی «Delete» در استودیو محصول را **آرشیو** می‌کند (`archived_at`). دلیلش این است که سفارش‌های قبلی به محصول اشاره دارند. همین جایگزین کلید `delishop-hidden` فعلی هم می‌شود: دیگر فرقی بین محصول اولیه و محصول اضافه‌شده نیست.

**ترتیب:** ۱۶ محصول اولیه `position` ۱ تا ۱۶ می‌گیرند و هر محصول جدید `max(position) + 1`. فروشگاه بر اساس `position` صعودی و استودیو بر اساس `created_at` نزولی مرتب می‌کند؛ همان رفتار فعلی.

```
Table: orders
- id                 (uuid, PK)
- number             (integer, unique, not null, default nextval('order_number_seq'))
                     sequence از ۱۰۰۱ شروع می‌شود؛ جای عدد تصادفی فعلی که ممکن است تکراری شود
- status             (order_status, not null, default 'awaiting_review')
- customer_name      (text, not null)
- customer_phone     (text, not null)            نرمال‌شده: ۱۱ رقم لاتین که با 09 شروع می‌شود
- total              (integer, not null)         به تومان؛ روی سرور حساب می‌شود
- receipt_key        (text, not null)            کلید فایل در باکت خصوصی
- receipt_mime       (text, not null)
- admin_note         (text, null)
- status_changed_at  (timestamptz, not null, default now())
- created_at         (timestamptz, not null, default now())
- updated_at         (timestamptz, not null, default now())

Index: orders(status, created_at desc)   لیست سفارش‌ها در استودیو با فیلتر وضعیت
Index: orders(customer_phone)            پیدا کردن سفارش وقتی مشتری تماس می‌گیرد
```

```
Table: order_items
- id            (uuid, PK)
- order_id      (uuid, FK → orders.id, on delete cascade, not null)
- product_id    (uuid, FK → products.id, on delete set null, null)
- product_name  (text, not null)      عکس فوری از نام در لحظه‌ی خرید
- unit_price    (integer, not null)   عکس فوری از قیمت در لحظه‌ی خرید
- quantity      (integer, not null, check quantity between 1 and 20)

Index: order_items(order_id)
```

**سبد خرید در دیتابیس نمی‌رود.** مشتری حساب ندارد، پس سبد مثل الان در `localStorage` همان مرورگر می‌ماند، فقط به شکل `{ productId, qty }` به‌جای کپی کامل اطلاعات محصول.

**بخش‌هایی که بعد از MVP بزرگ می‌شوند:**

- `orders` آدرس و هزینه‌ی ارسال ندارد، چون فرم فعلی هم ندارد (سؤال باز ۲).
- موجودی انبار وجود ندارد. اگر هر محصول تک است، ستون `stock` و رزرو هنگام سفارش لازم می‌شود (سؤال باز ۳).
- با اضافه شدن درگاه پرداخت، جدول `payments` لازم می‌شود (تراکنش، کد پیگیری، وضعیت).

## ۴. طراحی API

همه‌ی مسیرها زیر `/api` هستند. شکل خطا همیشه یکسان است:

```
{ "error": { "code": "validation_failed", "message": "Phone number must have 11 digits.", "fields": { "phone": "…" } } }
```

کدهای مشترک: `400 validation_failed`، `401 not_logged_in`، `404 not_found`، `413 file_too_large`، `415 unsupported_file_type`، `429 rate_limited` (با هدر `Retry-After`).

### عمومی

```
GET /api/health
Auth: ندارد
Response 200: { "ok": true, "db": "up" }
Response 503: { "ok": false, "db": "down" }
```

```
GET /api/products
Auth: ندارد
Cache-Control: public, max-age=60
Response 200: {
  "products": [
    {
      "id": "0b6e…",
      "name": "Super Fox",
      "category": "Keychains",
      "color": "orange",
      "price": 200,
      "story": "This is Super Fox. He wears a black mask…",
      "drawing": {
        "url": "https://media.example.ir/products/0b6e…/drawing-k3j9.webp",
        "width": 1125,
        "height": 1500,
        "crop": { "x": 150, "y": 370, "w": 900, "h": 1000, "clip": "none" }
      },
      "photoUrl": "https://media.example.ir/products/0b6e…/photo-a81c.webp",
      "voiceUrl": null
    }
  ]
}
```

`drawing.crop` برای محصولات جدید `null` است (کل تصویر). این شکل مستقیم به نوع `Product` فعلی فرانت‌اند (`src`، `iw`، `ih`، `x`، `y`، `w`، `h`، `clip`) تبدیل می‌شود و کامپوننت‌ها عوض نمی‌شوند.

```
POST /api/orders
Auth: ندارد
Rate limit: ۱۰ سفارش در ساعت برای هر IP
Body: multipart/form-data
  name     string، ۱ تا ۶۰ نویسه
  phone    string؛ ارقام فارسی و عربی هم قبول می‌شوند و نرمال می‌شوند؛ بعد از نرمال‌سازی باید 09 و ۱۱ رقم باشد
  items    رشته‌ی JSON: [{ "productId": "uuid", "quantity": 1 }]، ۱ تا ۳۰ قلم، تعداد هر قلم ۱ تا ۲۰
  receipt  فایل: jpeg یا png یا webp یا heic، حداکثر ۵ مگابایت
Response 201: { "number": 1042, "total": 450, "status": "awaiting_review" }
Response 400: validation_failed
Response 409: { "error": { "code": "product_unavailable", "productIds": ["…"] } }
              محصول بعد از رفتن به سبد آرشیو شده است
Response 413 / 415 / 429
```

### ورود

```
POST /api/auth/login
Auth: ندارد
Rate limit: ۵ تلاش ناموفق در ۱۵ دقیقه برای هر ترکیب IP و نام کاربری
```

## ۵. احراز هویت و دسترسی

- **روش:** نشست سمت سرور با کوکی `HttpOnly`، نه JWT. پنل مدیریت با فرانت‌اند هم‌دامنه است، پس کوکی ساده‌ترین روش است. نشست را می‌شود فوری باطل کرد (خروج، تغییر رمز) و هیچ توکنی در جاوااسکریپت در دسترس نیست که با XSS دزدیده شود.
- **ساخت یا سرویس آماده:** خودمان می‌سازیم. کل کار دو جدول و حدود صد خط کد است. Auth0، Clerk و مشابه‌ها برای یک مدیر زیادی‌اند و ممکن است از ایران در دسترس نباشند.
- **ورود:** نام کاربری با حروف کوچک مقایسه می‌شود و رمز با `argon2.verify`. اگر نام کاربری وجود نداشته باشد هم یک verify ساختگی اجرا می‌شود تا زمان پاسخ لو ندهد که نام کاربری درست بوده.
- **نشست:** توکن تصادفی ۳۲ بایتی (`crypto.randomBytes`) در کوکی `ds_session`. در دیتابیس فقط هش SHA-256 آن ذخیره می‌شود. عمر نشست ۱۴ روز است و اگر در ۷ روز آخر استفاده شود تمدید می‌شود. با هر ورود نشست جدید ساخته می‌شود.
- **خروج:** ردیف نشست حذف و کوکی پاک می‌شود. با تغییر رمز، همه‌ی نشست‌های آن مدیر حذف می‌شوند.
- **ساخت حساب مدیر:** مسیر ثبت‌نام وجود ندارد. حساب با `npm run create-admin` از خط فرمان ساخته می‌شود (نام کاربری و رمز را می‌پرسد). همین اسکریپت برای تغییر رمز هم به کار می‌رود.
- **مجوزها:** یک نقش واحد: هر مدیر واردشده به همه‌ی مسیرهای `/api/studio/*` دسترسی دارد. یک میان‌افزار `requireAdmin` روی کل گروه `/api/studio` نصب می‌شود، نه روی تک‌تک مسیرها، تا مسیری جا نیفتد.
- **CSRF:** کوکی `SameSite=Lax` به‌علاوه‌ی میان‌افزار `csrf()` خود Hono که روی همه‌ی درخواست‌های غیر GET هدر `Origin` را با دامنه‌ی سایت مقایسه می‌کند.
- **Multi-tenancy:** لازم نیست؛ یک فروشگاه است.

## ۶. زیرساخت و دیپلوی

### محیط‌ها

- **توسعه‌ی محلی:** PostgreSQL محلی (نصب مستقیم، یا Docker؛ اگر Docker Hub از ایران باز نمی‌شود از میرور داخلی استفاده کنید). فایل‌ها در `server/uploads/`. سرور با `tsx watch` روی پورت 3000 و Vite روی 5173 با پروکسی:

  ```ts
  // app/vite.config.ts
  server: { proxy: { '/api': 'http://localhost:3000' } }
  ```

- **production:** یک اپ Node.js روی لیارا که هم API را جواب می‌دهد هم `app/dist` را سرو می‌کند، یک PostgreSQL مدیریت‌شده و دو باکت Object Storage (`media` عمومی و `receipts` خصوصی).
- **staging:** برای شروع لازم نیست. وقتی کاربر واقعی دارید، یک اپ دوم با دیتابیس جدا روی همان هاست بسازید.

### مسیر دیپلوی

1. روی هر push و pull request، GitHub Actions اجرا می‌کند: `npm ci`، تایپ‌چک، lint، تست‌ها (با یک PostgreSQL به‌عنوان service container) و بیلد هر دو پروژه.
2. روی push به `main`: بیلد فرانت‌اند و سرور، اجرای مایگریشن‌ها (`drizzle-kit migrate`) و بعد `liara deploy` با توکن ذخیره‌شده در GitHub Secrets.
3. اگر دیپلوی از GitHub Actions به هاست ایرانی به خاطر محدودیت ارتباط بین‌المللی شکست خورد، همان دستورها را از کامپیوتر خودتان با CLI لیارا اجرا کنید.

### متغیرهای محیطی

همه در `server/src/env.ts` با Zod خوانده می‌شوند. اگر یکی کم باشد، سرور اصلاً بالا نمی‌آید. فایل `.env` در git نمی‌رود و `.env.example` بدون مقدار واقعی commit می‌شود.

### پایش (مانیتورینگ)

- لاگ‌های pino در داشبورد هاست. سطح `info` برای هر درخواست، `error` با stack trace. شماره‌ی موبایل، رمز و محتوای فایل‌ها هیچ‌وقت لاگ نمی‌شوند.
- `GET /api/health` برای health check هاست و یک سرویس uptime.
- Sentry معمولاً از ایران در دسترس نیست. برای MVP همان لاگ‌ها کافی است؛ بعداً می‌شود GlitchTip را خودمیزبان راه انداخت.
- بکاپ: بکاپ روزانه‌ی دیتابیس مدیریت‌شده را فعال کنید و یک‌بار بازگردانی آن را امتحان کنید. سفارش‌ها و رسیدها سند مالی فروشگاه‌اند.

### هزینه‌ی تقریبی

کوچک‌ترین پلن هر سرویس کافی است: اپ Node با حدود ۵۱۲ مگابایت رم، کوچک‌ترین PostgreSQL، و چند گیگابایت Object Storage. قیمت‌های تومانی مرتب عوض می‌شوند؛ قیمت روز را از سایت هاست ببینید. جایگزین خارجی: Railway حدود ۵ تا ۱۰ دلار در ماه، و Cloudflare R2 تا ۱۰ گیگابایت رایگان.

## ۷. سرویس‌های بیرونی

### Object Storage (لیارا یا ابر آروان) — در MVP

- **اتصال:** API سازگار با S3 از طریق `@aws-sdk/client-s3` با `forcePathStyle: true`.
- **داده:** آپلود هنگام افزودن محصول و ثبت سفارش؛ خواندن فایل‌های عمومی مستقیم توسط مرورگر؛ خواندن رسیدها فقط از مسیر `/api/studio/orders/:id/receipt`.
- **خرابی:** اگر آپلود شکست بخورد، درخواست با `503` و پیام «دوباره تلاش کنید» رد می‌شود و هیچ ردیفی در دیتابیس ساخته نمی‌شود. اگر خواندن فایل‌های عمومی کند باشد، فقط تصاویر فروشگاه دیر بار می‌شوند و API کار می‌کند.
- **آماده‌سازی:** دو باکت (یکی عمومی، یکی خصوصی)، یک کلید دسترسی با مجوز فقط همین دو باکت، و تنظیم CORS باکت عمومی برای GET از دامنه‌ی سایت.

### پیامک به مدیر (کاوه‌نگار یا sms.ir) — اختیاری

- **اتصال:** REST API سرویس، بعد از ثبت موفق سفارش. متن: «سفارش ۱۰۴۲ به مبلغ ۴۵۰ تومان ثبت شد».
- **خرابی:** یک بار تلاش مجدد بعد از ۳۰ ثانیه، بعد فقط لاگ. سفارش در هر حال ثبت شده و در استودیو دیده می‌شود.
- **آماده‌سازی:** حساب، شماره‌ی فرستنده و کلید API. برای پیامک‌های تبلیغاتی و خدماتی قوانین متفاوت است؛ این پیامک فقط به خود مدیر می‌رود.

### درگاه پرداخت آنلاین (زرین‌پال و مانند آن) — بعد از MVP

پرداخت فعلی کارت‌به‌کارت با تأیید دستی رسید است. درگاه آنلاین بررسی دستی و خطر رسید جعلی را حذف می‌کند، ولی نماد اعتماد (اینماد) و مدارک کسب‌وکار می‌خواهد. وقتی لازم شد: جدول `payments`، مسیر `POST /api/orders` که به درگاه redirect می‌کند و مسیر callback که پرداخت را تأیید و سفارش را `confirmed` می‌کند.

## ۸. امنیت

- **رمزنگاری:** HTTPS اجباری (TLS را هاست می‌دهد) و هدر HSTS. رمزها با argon2id هش می‌شوند. توکن نشست فقط به‌صورت هش ذخیره می‌شود. رمزنگاری دیسک دیتابیس و باکت‌ها با خود هاست است.
- **اعتبارسنجی ورودی:** هر بدنه، پارامتر و query با Zod روی سرور چک می‌شود؛ چک‌های فرانت‌اند فقط برای راحتی کاربرند.
- **فایل‌ها:** نوع فایل از روی بایت‌های اول آن تشخیص داده می‌شود (پکیج `file-type`)، نه از پسوند یا Content-Type مرورگر. محدودیت حجم هم با `bodyLimit` روی کل درخواست اعمال می‌شود و هم جدا برای هر فایل. تصاویر محصول با sharp دوباره ساخته می‌شوند؛ این کار متادیتای EXIF، از جمله موقعیت GPS عکس‌های موبایل، را پاک می‌کند. رسید همان‌طور که هست ذخیره می‌شود، ولی فقط مدیر آن را می‌بیند و با `Content-Disposition` مناسب سرو می‌شود. SVG هیچ‌جا قبول نمی‌شود.
- **داده‌های حساس:**
  - نام و موبایل مشتری و عکس رسید (که ممکن است شماره‌ی کارت یا اطلاعات بانکی مشتری را داشته باشد) فقط در دیتابیس و باکت خصوصی هستند و فقط مدیر به آن‌ها دسترسی دارد.
  - پیشنهاد: رسیدهای سفارش‌های ارسال‌شده یا ردشده بعد از ۱۲ ماه با همان کار روزانه پاک شوند.
  - صدا و نقاشی‌ها کار یک کودک است؛ نام کامل و عکس چهره‌ی او را در داستان‌ها و فایل‌ها نگذارید.
- **محدودیت نرخ:** ورود ۵ تلاش ناموفق در ۱۵ دقیقه، سفارش ۱۰ در ساعت برای هر IP، و بقیه‌ی مسیرها ۳۰۰ در دقیقه. اگر سرور پشت پروکسی هاست است، IP واقعی را از هدری بخوانید که هاست تضمین می‌کند، وگرنه همه یک IP دارند. اگر سفارش اسپم آمد، کپچا (مثلاً ArCaptcha) به فرم پرداخت اضافه شود.
- **هدرها:** میان‌افزار `secureHeaders()` هونو، با Content-Security-Policy که فقط دامنه‌ی خود سایت، آدرس باکت media و Google Fonts را مجاز می‌کند.
- **قیمت‌ها:** جمع سفارش همیشه روی سرور حساب می‌شود.
- **وابستگی‌ها:** Dependabot روی ریپو و `npm audit --audit-level=high` در CI.
- **قوانین:** GDPR برای مشتری‌های داخل ایران الزامی نیست، ولی همان اصول را رعایت کنید: فقط داده‌ی لازم را بگیرید، دسترسی را محدود کنید و داده‌ی قدیمی را پاک کنید. برای درگاه پرداخت، اینماد لازم می‌شود.

**سؤال‌های باز (قبل یا حین ساخت باید جواب داده شوند):**

1. **هاست:** سایت در ایران میزبانی می‌شود یا خارج؟ این طرح ایران را فرض کرده است.
2. **ارسال:** فرم پرداخت آدرس نمی‌گیرد و هزینه‌ی ارسال ندارد. سفارش را چطور به مشتری می‌رسانید؟ آیا فیلد آدرس و هزینه‌ی ارسال لازم است؟
3. **موجودی:** هر محصول تک است یا سفارشی ساخته می‌شود؟ اگر تک است، باید موجودی داشته باشد و بعد از فروش از فروشگاه برداشته شود.
4. **اطلاع از سفارش:** فقط صفحه‌ی سفارش‌ها در استودیو کافی است یا پیامک هم می‌خواهید؟
5. **ویرایش محصول:** استودیو الان فقط افزودن و حذف دارد. ویرایش قیمت و داستان در MVP لازم است؟ (از نظر API یک `PATCH` ساده است؛ کار اصلی رابط کاربری آن است.)
6. **داده‌ی فعلی:** محصولاتی که الان در استودیوی مرورگر خودتان اضافه کرده‌اید باید به سرور منتقل شوند؟ اگر فقط محصول آزمایشی است، لازم نیست.
7. **تعداد مدیرها:** یک نفر یا چند نفر؟ اگر چند نفر، ثبت اینکه چه کسی وضعیت سفارش را عوض کرده مفید است.

## ۱۱. تغییرات لازم در فرانت‌اند

1. **`app/vite.config.ts`:** پروکسی `/api` به `http://localhost:3000`.
2. **`app/src/lib/api.ts` (جدید):** یک `fetch` کوچک که JSON می‌فرستد و خطاهای `{ error }` را به یک `ApiError` با `code` تبدیل می‌کند. در صورت تمایل از کلاینت RPC هونو (`hc<AppType>`) برای نوع‌های مشترک استفاده کنید.
3. **`app/src/lib/store.ts`:**
   - `useCatalog` با `useQuery(['products'])` جایگزین شود و خروجی API به نوع `Product` فعلی تبدیل شود، تا `Shop`، `Inventory`، `Thumb` و `ProductModal` عوض نشوند.
   - سبد در `localStorage` بماند، ولی به شکل `{ productId, qty }`.
   - `deleteProduct` به `DELETE /api/studio/products/:id` وصل شود.
4. **`app/src/lib/auth.ts` و `RequireLogin.tsx`:**
   - ورود و خروج به `/api/auth/login` و `/api/auth/logout` وصل شوند.
   - وضعیت ورود از `useQuery(['me'])` بیاید و `RequireLogin` تا جواب نیامده چیزی نشان ندهد.
   - هش رمز از کد فرانت‌اند حذف شود.
5. **`app/src/pages/Admin.tsx`:**
   - `canvas.toBlob` به‌جای `toDataURL`.
   - صدای ضبط‌شده به‌صورت `Blob`.
   - ارسال با `FormData`، و بعد از موفقیت، تازه‌سازی کش محصولات.
6. **`app/src/pages/Checkout.tsx`:**
   - فایل رسید به‌صورت `File` نگه داشته شود (پیش‌نمایش با `URL.createObjectURL`) و با `FormData` فرستاده شود.
   - شماره‌ی سفارش بعد از جواب سرور نشان داده شود، نه قبل از آن.
   - خطای `409` (محصول ناموجود) با پیام مناسب نمایش داده شود.
   - **ایراد فعلی:** فیلتر شماره موبایل (`/[^\d\s+]/g`) ارقام فارسی را پاک می‌کند، پس کسی که با صفحه‌کلید فارسی شماره وارد کند نمی‌تواند سفارش بدهد. ارقام فارسی و عربی باید به لاتین تبدیل شوند، نه حذف.
7. **`app/src/pages/Orders.tsx` (جدید):** صفحه‌ی سفارش‌ها در `/studio/orders`، پشت `RequireLogin`، با لینک در هدر استودیو.
